# Security review: everything that moves value

Scope: collects, tips, remix royalties, the protocol fee, weekly rewards, the signed scores that feed rewards, and how any treasury or payout key is held. Reviewed on 2026-10-10 together with the change that makes collects and tips real Solana payments. This is an internal review, not an independent audit; mainnet still needs one (see the checklist at the end).

## How money moves now

- **Simulated ledger (no `GP_SOLANA_CLUSTER`, or inside Claude):** unchanged. Balances are devSOL numbers replayed from signed ledger entries. Nothing touches Solana.
- **Real network (`GP_SOLANA_CLUSTER=devnet`, `testnet` or `mainnet-beta`):** a collect or tip is a Solana transaction that the player's own wallet signs. It pays the creator, the parent and grandparent creators and the treasury directly, in one transaction, with the memo `gameplay:<ledger id>`. The ledger entry then carries the transaction signature (`b.chain`). Every page looks the payment up on Solana (through `/api/chain/txs`) and only counts the entry if the payment checks out. Balances shown are read from Solana.

ClaudePlay never holds funds and the server never holds a private key.

## Findings and fixes

| # | Finding | Status |
| --- | --- | --- |
| 1 | Collects and tips only changed numbers in the ledger, so "earnings" were not money anyone could withdraw. | **Fixed.** On a real network they are wallet-to-wallet Solana transfers. |
| 2 | A real payment could be claimed for the wrong action, by the wrong person, or twice. | **Fixed.** `checkPayment` (src/core.js) requires: the transaction succeeded, its signer is the ledger entry's wallet, its memo names that exact entry id, and each recipient got at least its share. A signature counts once across the whole ledger. Tests: `test/solana.test.mjs`. |
| 3 | A treasury key on the server would be a single point of theft. | **Fixed by design.** The treasury is only a public address (`GP_TREASURY`). The server refuses to start if the value is not a 32-byte address, so a pasted secret key is rejected. |
| 4 | The built-in browser wallet keeps its key in `localStorage`, where any script bug could read it. | **Fixed for mainnet.** On mainnet, payments must come from a wallet app (Phantom, Solflare, Backpack, or any Wallet Standard wallet) and importing keys is disabled. The built-in wallet stays for devnet and for signing game actions. |
| 5 | A published game could send whatever a player types to another site. | **Fixed.** Games run in a sandboxed frame (no same-origin, so no access to the page, its storage or wallets) and now also under a Content Security Policy that blocks every network request (`withSDK` in src/kits.js). AI-built games are also instructed never to ask for a wallet or seed phrase. |
| 6 | The server's Solana endpoint could be used as a free general-purpose RPC relay. | **Fixed.** `/api/chain/send` relays only ClaudePlay payments: one signer, System transfers, a `gameplay:` memo and optional priority-fee settings. Requests are limited to 120 a minute per visitor and 16 KB per body. The faucet allows two drops a day per visitor and per address and does not exist on mainnet. |
| 7 | Tips had no upper bound. | **Fixed.** Tips are capped at the same maximum as collect prices in both modes. |
| 8 | Nothing stopped a deploy from pointing at mainnet by accident. | **Fixed.** Mainnet starts only with `GP_ALLOW_MAINNET=yes` and a treasury address. Devnet is the default in `render.yaml`. |
| 9 | Signing confusion between ledger messages and Solana transactions from the same key. | **Not exploitable.** Ledger messages start with `GAMEPLAY/v1`; Solana messages start with byte `0x01`. Session keys from wallet apps can sign game actions for 7 days but cannot move funds: every payment needs the wallet app's own approval. |
| 10 | Pages trust the site's own server to report payments. A compromised server could make fake collects look paid (inflating stats and editions). It cannot take anyone's money, because payments go wallet to wallet. | **Open.** Fix with the on-chain registry (Anchor program) in the roadmap, or by checking payments against a second RPC provider. |
| 11 | A payment can land while its ledger entry is refused (the last edition sells out in between, or the tab closes). The money is already with the creator; there is no refund path. | **Mitigated.** The page checks the action with a stand-in payment before asking the wallet, and keeps a confirmed payment in the browser and records it on the next visit (for 24 hours). A full fix is the on-chain program enforcing edition caps atomically. |
| 12 | Weekly GPLY rewards rest on scores the player's own page reports and on one-account-per-player counting, which a determined player can game with many accounts. | **Open, acceptable while GPLY is points.** In real-network mode no SOL is paid out as rewards (the ledger's treasury balance stays 0). Before GPLY or SOL rewards carry value: server-side score checks, sybil resistance, and a Merkle distributor. The owner key (`GP_ADMIN_KEY`) settles epochs; keep the owner link private. |
| 13 | Spark packs are paid to the treasury in the simulated ledger. | **Disabled on real networks** until they are built as real payments. |
| 14 | Switching an existing site from the simulated ledger to a real network leaves old simulated collects and tips without payments. | **By design.** Those entries show as unpaid and stop counting; games, scores and handles carry over. |
| 15 | On mainnet, the site's wording still said balances were test tokens and no real funds moved. | **Fixed.** The footer, front page, FAQ and earnings copy say plainly that collects and tips are real SOL. |
| 16 | On mainnet, real SOL could be paid to a creator whose key lives only in their browser's storage, and is lost if they clear it. | **Fixed.** On mainnet, publishing needs a wallet app, and the page refuses to pay a creator whose wallet is a browser key. |
| 17 | The public mainnet RPC rate-limits and often refuses to relay transactions from servers, so payments would fail. | **Fixed.** Mainnet will not start without `GP_SOLANA_RPC`. |
| 18 | Pro passes are paid in SOL to the treasury. A payment could be claimed twice, for the wrong account, or for less than the price. | **Fixed.** `claim()` in server/plans.mjs requires a successful transaction whose signer paid `GP_TREASURY` at least the price, with the memo `gameplay:<pro id>` derived from the claiming account; each signature unlocks Pro once (`kv.once`). Tests: `test/server.test.mjs`. |
| 19 | Daily AI build limits were kept in memory, so a restart (Render's free plan sleeps) reset them and let a visitor exceed the cap. | **Fixed.** Counts live in Upstash Redis (or `kv.json`) with atomic increments. Free builds count per network address and toward the site-wide cap; set a monthly spend limit in the Anthropic Console as the hard backstop. |
| 20 | Creators can upload pictures, which are sent to Claude and published inside their game files. Oversized or malformed uploads could break a build or the gallery, and a picture can be offensive. | **Partly fixed.** The browser shrinks pictures to at most 256 px and re-encodes them as PNG; `checkRequest()` accepts at most 4 PNGs of at most 48,000 base64 characters with checked names and sizes, and the pictures block is built with `JSON.stringify` from those checked values. The game frame's CSP only allows `data:` images. **Open:** pictures are not screened before publishing yet (step 4 of the Playground plan adds an automatic check). |
| 21 | Multiplayer rooms relay messages between players' browsers. A stranger could impersonate a player, flood a room, or push something harmful into the page. | **Fixed.** Each player gets a random token with their id and must send it with every message; messages are capped at 2 KB and about 40 a second per player, rooms at 16 players (`GP_ROOM_PLAYERS`, at most 32), room opening at 30 an hour and open streams at 12 per network address. The server never reads messages; the page only forwards them into the sandboxed game frame with `postMessage`, and names are cleaned to letters, digits, spaces, `_` and `-`. Room codes are random, and a room only opens for the game it was made for. A daily traffic budget (`GP_ROOM_MB_DAY`, 100 MB) keeps a flood of room traffic from using up the host's monthly bandwidth. |
| 22 | Published games and uploaded pictures were not screened, so the public arcade could carry harmful content, phishing (asking for seed phrases) or games that try to reach the internet. | **Fixed (automatic screening).** Pattern checks plus a Claude review of code, title, description and pictures run before publishing; the server signs the file's hash with an HMAC token and the gallery refuses game files without one, so a modified page cannot skip the check. Unclear reviews and outages block publishing. **Open:** reviews inside the Claude artifact run in the viewer's browser and are not enforced; reports and owner delisting remain the backstop. |
| 23 | The play-test review (`POST /api/playtest`) sends pictures to Claude, so it could be misused as a free image-reading service. | **Limited.** It takes only one to three small JPEG screenshots and a short run log, uses a fixed review prompt on Haiku with 500 output tokens, returns nothing but up to four short problem lines, allows 60 reviews an hour per visitor and 1,000 a day across the site (`GP_DAILY_PLAYTESTS`, counted in the shared store so restarts don't reset it), and is off without an AI key. The game code is never sent with it. |
| 24 | Follows, friends boards and unlisted games are entries in the public ledger. | **By design, and said so in the app.** Unlisted only keeps a game out of Explore and the front page; anyone with the link or reading the ledger can still open it. Anyone with a friends board's invite link can join it (up to 100 members). Group names are cleaned and capped at 32 characters, and nothing private is stored. |

## Owner checklist before mainnet

Only Ken can do these. Nothing in the repo switches production to mainnet or moves real funds until Ken has done them and says go in the project thread.

1. **Fee wallet.** Create a wallet you control in Phantom or Solflare (a Ledger hardware wallet is better). Keep its recovery phrase offline. Never paste the phrase or a private key into chat, the repo, Render, or any website. Give the site only its public address, as `GP_TREASURY`.
2. **Try it on devnet.** Deploy on Render, set `GP_TREASURY`, switch your wallet app to devnet, and collect and tip a game with free devnet SOL.
3. **Independent security audit** of the payment flow and the server, and **a legal opinion** on real-money tips, royalties and the protocol fee: the Philippine SEC's CASP Rules (in force since 5 July 2025), the BSP's VASP rules, tax, and any country you will serve. ClaudePlay stays non-custodial, sells no token and offers no peso-to-crypto exchange.
4. **Moderation** of published games (the content screening and queue in the roadmap).
5. **Say "go" in the thread.** Then the deploy changes are: `GP_SOLANA_CLUSTER=mainnet-beta`, `GP_ALLOW_MAINNET=yes` and your own RPC endpoint in `GP_SOLANA_RPC` (the server refuses mainnet without one). The site's wording switches to real SOL by itself.
